Dev Log · #040

Twenty-Three Quiet Time Bombs

A Full Structural Audit That Started With a Tech Tree Collision

September 3, 2026

A Screen That Kept Collapsing

While polishing the tech tree window, a bug showed up — the window kept rendering wrong. The detail panel area would shrink to half its intended space, or less. It repeated every time a different city got selected during testing.

Digging into the cause turned up a clear picture. One UI node, content_root, was being touched simultaneously by two scripts that had no idea the other existed.

  • worldmap_main.gd's _refresh_domestic_tech_tree_overlay_mvp() — clears this node entirely and rebuilds it from scratch every time the selected city changes: header_row → split (national/city tree) → inspector (detail info), in that order — the originally intended, correct layout.
  • worldmap_tech_tree_split_detail_test_controller.gd's _process() — running every frame, quietly detaching the split and inspector nodes built above and re-wrapping them into a 42%/58% ratio.

The problem was that neither knew about the other. The moment a city click triggered the first script to clear content_root, the node the second script had built was still sitting in the tree that frame — only "scheduled for deletion" via queue_free(), not actually gone yet. If the first script added its new nodes right at that moment, two sets of space-competing nodes briefly existed on screen at once. A VBoxContainer splits remaining space evenly between such nodes, so the detail panel collapsing was the inevitable result.

One Room, Two People

Here's the metaphor that made the situation click. Two people are tidying the same room, each on their own. One person (A) clears the entire room and rearranges the furniture from scratch every time a new guest arrives. The other (B) quietly follows behind, re-arranging what A just placed into a nicer 42:58 split. Neither knows about the other. The instant A clears the room, the furniture B had just rearranged is still sitting there, not fully removed — and if A then moves in new furniture on top of that, for one brief moment the room holds two competing sets of furniture trying to claim the same space. Neither ends up settling properly; both get crushed into a corner.

The fix broke down into three steps.

  • Build it complete from the start — instead of keeping B separate, have A build the finished "42:58 split room" in one pass from the beginning.
  • Carry over the rules B knew too — B wasn't just rearranging furniture; it also held a rule: "national topics go left, city topics go right." Dropping B without carrying this rule over would stop the collapsing, but the feature itself would vanish. So this rule had to be handed off to A as well.
  • Clean up the now-unnecessary contract with B — once steps 1 and 2 are done, B has nothing left to touch and naturally stops mattering on its own. The file still exists, though, so this final step formally retires it to avoid confusion later.

Was This Just a One-Off Problem?

Fixing the bug raised a question: could this pattern exist elsewhere too? So the entire scripts/worldmap/ui/ folder got scanned.

23 test_controller-type scripts existed. Of those, exactly two others — besides the tech tree one — used the identical pattern: polling every frame via _process() and directly reaching into a node built by worldmap_main.gd. One touched garrison cards; the other touched the left/right HUD panels and the prime minister/governor cards.

Fortunately, only the tech tree case had actually broken so far. The reason was clear — across all of worldmap_main.gd, exactly one destructive function existed that "clears children entirely and rebuilds from scratch," and it belonged only to the tech tree. The other two targets (garrison cards, HUD panels) only get their values updated, never cleared and rebuilt. That's why the same bug hasn't triggered there — yet.

But the core point was that all three shared the same underlying risk. The bug only fires when "destructive rebuild" and "external polling patch" overlap — right now, that overlap just happens to exist only in the tech tree. The moment either of the other two gets refactored into a "clear and rebuild" pattern, the same collision could resurface.

A Three-Step Response

Step 1 — Fix what actually broke. The separate controller's after-the-fact re-wrapping structure got removed, and the final 42:58 layout got merged directly into worldmap_main.gd's owning function. National and city detail views got properly separated, the watermark got made conditional, and rebuilds now detach and queue_free immediately.

Step 2 — Audit the two risky remaining cases. Code didn't get moved blindly here. First came determining exactly what _process() was looking for, which nodes it directly modified, whether main-side code currently rebuilds those nodes, and whether the feature had already stabilized. The verdict split three ways: safe-but-temporary patches stay as-is with the risk documented; anything stabilized and worth promoting gets merged into proper code; risky polling structures get converted to a signal-based approach or merged into the owning function.

Step 3 — Lock the prevention rule into the docs. This turned out to be the most valuable outcome of the whole bug.

A UI subtree that gets destructively (clear+rebuild) regenerated must never be the target of a separate controller polling it via _process(). It must either (a) have its logic merged directly into the owning function, or (b) emit a Signal once the rebuild finishes, with any external script reacting only once, on receiving that Signal.

Going forward, whenever a new test_controller gets added, the verification routine now includes listing which node paths it looks up inside _process() and cross-checking whether worldmap_main.gd contains a function that clears and rebuilds that same node path. Longer term, test_controllers that have already stabilized with no further changes get periodically promoted into the main body or a proper system file — managing the sheer count of files still carrying the "test_controller" label.

The goal of this cleanup was never to move all 23 into the main body. It was to audit all 23 and only touch the ones that are genuinely risky or worth promoting — that line got drawn clearly.

The Branches Got Cleaned Up Too

Something else surfaced while fixing the bug. Two large ongoing efforts — the map screen overhaul and the battle movement experiment — had zero relationship to each other, yet were tangled together in the same branch. As it stood, there was no way to say "let's just lock in this one piece" without dragging the other along.

So the branches got fully separated. Using main as the reference point, each file's final state from the original branch got sorted and moved by path, with the original branch preserved untouched. Here's how it split:

  • WorldMap → feature/worldmap-territory-techtree-hud (106 files)
  • Battle Iso → feature/battle-iso-movement (23 files)
  • AI Workflow Docs → docs/ai-implementation-workflow (2 files)
  • Hero Cutin Perf → perf/hero-cutin-registry-cache (1 file)

File overlap between WorldMap and Battle Iso came out to zero.

Today in One Line

A screen kept rendering wrong, and fixing it turned out to mean two separate pieces of code touching the same screen without either knowing the other existed. Fixing that raised the question "is this happening anywhere else?" — and a full codebase scan turned up two more instances of the same pattern. Along the way, it also became obvious that two currently unrelated efforts had been sitting in the same branch this whole time. A day that started with one screen bug ended up revealing that the way things had been working needed a cleanup of its own.
