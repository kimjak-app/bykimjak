Dev Log · #052

An Emergency Meeting in the Middle of the Night

Finding a way through EASTWAR's 3D problems with QUORUM

October 28, 2026 · EASTWAR's 3D battlefield and collaboration through QUORUM

I continued planting pine trees on the battlefield of EASTWAR (project name: Samguk WAR). Yesterday I worked on the shape and weight of a single tree; today I was grouping those trees into forests. For now, I decided to make forests impassable. They would add scenery while also creating terrain that units would have to go around.

But every time I changed the forest layout, existing tests broke again. The tests for the new feature that blocks forest cells reportedly passed, yet the combat tests we had been running all along ran into problems. When Claude Coach reported that this was already the third time the forest work had conflicted with existing tests, I asked:

“Isn't it simple? Make clusters of trees and make them impassable in the Godot engine. Why is this so complicated?”

That question started today's emergency meeting in QUORUM.

The problem hiding behind blocking off a forest

Listening to Claude Coach's explanation, I learned that creating blocked cells was not the biggest obstacle. The forest layout we kept changing was also being applied to the battlefield used by the existing tests.

The game has regression tests to check that new work has not broken older features. Among them, Golden tests compare the current results against predetermined reference results. They are a kind of reference snapshot of how units move and how a battle ends under the same conditions.

But adding a new forest to that reference battlefield changes the routes. Units may detour or wait, producing results that differ from the old ones. We first needed to distinguish an actual code problem from a change to the test stage itself. This time, failures were reported in a defeat scenario and a test checking friendly roster cards. The exact cause of each still needed investigation.

What if we simply moved the trees somewhere that would not interfere with the tests, or changed the expected results each time? We might get past the immediate problem, but face the same dilemma the next time we moved the forest. I wanted to be free to experiment with the battlefield. If every layout change required reworking the existing tests too, the work would only become more cumbersome.

I called the coaches into QUORUM

I asked Claude Coach to organize the problem and the options so I could show them to the other coaches. Claude Coach prepared a briefing to share, and I took it into QUORUM and called in ChatCoach, Gemini Coach, and Grok Coach: ChatGPT, Gemini, and Grok, respectively. Together with Claude Coach, who is Claude, four AI coaches would review the problem.

QUORUM is an app I built with Codex for the AI orchestration I had really wanted to try. I made it to see the coaches' opinions in one place and pass along what was needed while designing and implementing EASTWAR's 3D battlefield and assets quickly and effectively. After using it to choose a pine tree yesterday, today I held a meeting about a development problem that had suddenly come up.

The AIs were not talking to each other on their own in this process. I asked the questions, read each reply, selected what needed joint review, and passed it along again. QUORUM is still at an early stage, and there were moments when I had to check input results myself. This capture even retains an input-failure notice. Rather than documenting a finished automatic relay feature, this is a record of continuing our collaboration while trying the app in real work.

The consensus: separate tests from layouts

The three coaches agreed on the broad direction. Preserve the reference environments for tests of existing combat, and make the new forest layouts something we explicitly select and apply separately.

Gemini Coach identified this as a problem of test brittleness: we needed to fix a structure where a small change in scenery could easily break existing tests. Grok Coach separated out which layout each environment should have and brought the three coaches' opinions together into a course of action. ChatCoach looked again for hidden assumptions and gaps in verification within that agreement.

This brought up the word “harness”: the setup that prepares the battlefield, units, and execution conditions for a test. Tests checking equivalence with the old 2D version would keep their empty battlefield, while existing 3D regression tests would retain their fixed environments from that time. We would explicitly apply the new forest layouts to T2-specific tests or scenes I compared visually. The idea was to separate these bundles of layouts into presets.

This did not mean removing every forest from every existing test. Some tests had already been built around a fixed set of blocked cells. Deleting that list could undermine existing verification instead. The first step was to establish what the actual reference environment had been and preserve that state.

The new forest needed its own checks

Separating tests from forest layouts leaves one question. What if the old tests are fine, but the new forest blocks the battlefield completely?

So we decided to add a separate reachability check: a test to see whether a path still allows friendly and enemy units to meet after placing the forest. The proposal was to check connectivity quickly with BFS, or breadth-first search, but not rely on that alone. We would cross-check against the movement pathfinding actually used by the game engine.

The visible trees and the actual impassable cells also needed to use the same coordinates. We could not have units stopping on treeless ground or walking straight through a forest. I also asked for separate checks for conflicts with rivers, starting positions, and reinforcement arrival cells.

Hills were another important issue. The candidate forest layout included hill cells. If we overwrote the terrain type from HILL to FOREST just because we were placing trees there, we could also change terrain information we intended to preserve. We chose to retain the hill property and handle the impassable attribute, blocked_cells, separately. However, whether this terrain change directly caused the test failures was still only a hypothesis, so I asked for confirmation through code and logs.

Whether to allow forests on hills, and how to choose the final clusters, remained my decisions. I kept the coaches' technical proposals separate from decisions about what I wanted the game to look like.

Turning the agreement into actual work instructions

After gathering the opinions, I passed them back to Claude Coach. Claude Coach turned them into overnight work instructions for Claude Code, as we call our coding coach, to execute.

Choosing a good direction did not mean immediately changing the code. First, I had the instructions call for preserving the existing work and investigating the causes separately in a temporary worktree, an isolated workspace. The instructions specified which baseline states to compare, which tests had to pass before moving on to modifications, and where to stop if the results differed from expectations.

Another review followed the first draft. ChatCoach pointed out that even if a particular cause seemed likely, we must not move into the modification stage if the existing baseline tests had not passed. The possibility of a failure caused by load was only a lead for further investigation, not permission to proceed anyway.

We also revisited assumptions about the order of code changes. We had thought one modification came first, but the reports alone did not establish the sequence. Claude Coach confirmed that the same assumption had entered its instructions and revised them to investigate the actual change history before comparing the effects separately.

This was an important part of the collaboration. We did not stop when several coaches chose the same answer. One coach reviewed another's proposal, and we rechecked the assumptions within that review as well, refining the instructions into a second version.

The final instructions said to stop if the baseline could not be confirmed, not to alter existing Golden expectations arbitrarily, and not to start T3, the next phase covering advance, retreat, repositioning, and reinforcements beyond the current scope. They also required the report to distinguish confirmed facts, estimates, and unknowns, and prohibited merging or pushing without separate approval.

Where we got to today

I handed Claude Code the instructions with the final additions incorporated. That is as far as the confirmed results go at the time of writing. Whether the code was successfully separated, whether the full CI passed, and whether units move correctly through the new forest layout must be established through the next work report and verification.

Still, today gave me an example of why I built QUORUM. Claude Coach organized the problem on the ground, and Gemini Coach, Grok Coach, and ChatCoach reviewed possible solutions and risks. I shared and selected their opinions, and Claude Coach brought them back together as instructions with an execution order and stop conditions. That connected the discussion to Claude Code's next assignment.

When we add rocks or fortifications later, their layouts will change many times too. Each time, we will need to distinguish what we can change freely, what we must preserve, and what we need to verify anew. Today's forest problem made us think through those boundaries together.

I think the orchestration I have wanted to try begins like this: asking the necessary questions, comparing different opinions, asking again about missed conditions, and then carrying that into actual work. QUORUM is still basic, but today we used it to try out our way of working together once more.
