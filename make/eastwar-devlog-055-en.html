The 3D World Map Takes Shape

From a Korean prototype to Korea, China, and Japan: a new setting for the existing 2D MVP

November 1, 2026 · Building EASTWAR’s 3D World Map

The 3D terrain we had tested on the Korean Peninsula now extends across mainland China and the Japanese archipelago. Today, I expanded the EASTWAR world map, developed under the working title Samguk WAR, to cover Korea, China, and Japan, and brought the regional layout from the existing 2D MVP onto it. After our earlier work on the 3D battlefield, the world around those battles is beginning to take shape too.

Bringing the existing 12 regions onto new terrain

The important part was not just making the map larger. It was carrying over the existing 12 regions: four in Korea, four in China, and four in Japan. Including Karakorum, the test scene now contains 13 cities.

We enabled castle and flag markers for all 13 cities and added Korean region labels. The labels appear and disappear according to zoom level. The aim was to make the regional layout readable from a distance and individual territories and castles identifiable up close. In these screenshots, all 13 cities belong to different factions as a test configuration for checking borders.

Borders that follow mountains and rivers

We also revised the boundaries on the terrain. In v2.3, straight borders were redrawn as winding lines following mountain ridges and rivers. We applied the same option A across every region, including Korea, while retaining the faction colors. With mountains and rivers shaping the land, I wanted the boundaries to follow that terrain as well.

We standardized faction colors on the v3 palette. Chu under Xiang Yu is green (#2E7D32), and the Mongols are teal (#17B3B0); both decisions are reflected in the porting plan. For rotating the map, input mode A, using right-click drag, is the default. The plan also retains the option to switch to mode B in settings.

From an external map build into the project

We also clarified how to work together. Grok Coach prepared map assets and patches outside the repository, while Claude Code handled importing and checking them inside it. Claude Coach organized the instructions and sequence so that work could continue without two people changing the same files at once. My responsibilities became clearer too: pass on the instructions, run the scene with F6 and judge whether it passes, and approve the final merge into main.

During the import, we renamed the 3D camera to avoid a naming conflict with the existing 2D camera and aligned Godot’s import settings files with the project. A byte-for-byte comparison of 129 imported files against the source package found no differences. Import errors and duplicate class names were both zero.

We updated the automated checks to Godot 4.6.2 and added a dedicated 3D world map workflow. After importing v2.3 with its revised borders, we also imported and pushed the v2.4 patch with castles, flags, and region labels to the working branch. Both the WorldMap3D checks and the existing C-track checks passed. I ran the scene with F6 and accepted it as well. This verification covers the standalone test scene; the main and integration branches were left untouched.

We recorded a few practical handoff rules too: download only the needed patch files rather than a whole Drive folder, put the baseline commit at the top of the patch notes, and state how many files changed or were added. Counts also need to distinguish between one city and the total. Clear handoffs mattered just as much as producing the map itself.

Carrying forward the game we built in 2D

The next focus is the interface and features of the existing 2D MVP. We will connect its world map HUD, tech trees, diplomacy, espionage, regional resources, and national information to the new 3D map. The goal is to retain the rules and data already implemented while moving the map used to display and interact with them into 3D.

Before connecting the systems, we audited the existing 2D coordinates without modifying them and incorporated the findings into the porting plan. We also corrected our understanding of refresh_tool: it overwrites the 2D camera even in the running game. The next camera integration stage must account for this behavior and prevent existing input handling from interfering with the new map.

The sequence starts with the camera and integration adapter. It then proceeds through selecting objects on the map, unifying colors, adding roads, and checking battle entry and graphics-memory release before switching over to the new map. These stages, 03 through 08, are still ahead. Bringing over the regional layout and markers today does not mean that the HUD and game features are already connected.

Next: measure performance and connect the game

Performance will be checked separately. We did not repeat measurements for v2.3 because only two border textures had changed, with their sizes and formats unchanged. The next benchmark will compare markers on and off under both d3d12 and Vulkan, measuring FPS and VRAM. Those results are not yet available in today’s record. A guard for the existing 2D camera’s keyboard input is also in the overnight work package, with results still pending.

The map that proved the approach on the Korean Peninsula now spans Korea, China, and Japan, and is inside the project where I can run it myself. Next comes making the existing game work on this terrain. Following the move to a 3D battlefield, the world map is beginning to stand on its own. I want to remember today as the day we prepared the setting for that next stage.
